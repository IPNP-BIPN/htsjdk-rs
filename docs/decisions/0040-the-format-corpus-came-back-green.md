# 0040. The format corpus came back green

**Status:** accepted
**Date:** 2026-09-01
**Closes:** [0022](0022-the-format-corpus-was-never-checked-against-the-oracle.md)

## What 0022 left open

Decision 0022 found one committed golden that no CI step had ever regenerated,
`crates/htsjdk-metrics/tests/data/format.txt.gz`, declared it as a suite with `status: unchecked`,
and generated it into a job whose name carries that status. It closed on a condition rather than an
answer:

> Until the `format` suite has run green in CI, the 99.73% figure describes a measurement made on an
> unpinned machine. If the first run diverges, the figure changes rather than the method: the number
> that survives is the one the oracle produces.

That mattered because decision 0011 established that metrics number formatting is **locale-dependent**,
and the oracle image pins `en_US` where a developer machine pins nothing. The one corpus whose
correctness depended on a property the container exists to guarantee was the one the container had
never seen.

## What the runs say

The suite has run on every push since, in the pinned `linux/amd64` container on real x86-64. From
the `oracle unchecked 1/1` job of the most recent CI run on `main`:

```text
regenerated FormatDump: 41678 lines (docker exit 0)
ok   format/FormatDump: compared=41612
suite=format status=unchecked cases=1 compared=41612 failed=0
```

The dump the container produced has the same 41,678 rows the committed corpus has, and the two
agree. The comparison is `named`, keyed on each row's bit pattern, so the 41,678 rows carry 41,612
distinct patterns and a pattern that appears more than once is compared once: `0`, `1` and the other
round values are generated by more than one of the harness's families.

So the corpus is what the pinned reference produces, and the README's **99.73%** is now a property
of the oracle rather than of the machine that first wrote the file. The status moves to
`oracle-backed`, and htsjdk-rs has no `unchecked` golden left.

## What this does not settle

Two things 0022 raised are untouched by this.

`tools/zlib-conformance` is still validated only on a developer machine: its README says the
comparison was run against OpenJDK 17.0.19 on macOS arm64 and is "not yet confirmed inside the
pinned `linux/amd64` container". It compares a Java run to a Rust run rather than a dump to a
golden, so the manifest does not cover it and neither does this decision. It stays open, as
decision 0001 lists it.

And the 112 divergent formattings are still divergent. They are blocked by a licence rather than by
difficulty (decision 0013); what changed here is that the count is now measured against the pinned
reference rather than assumed from a local run.
